本文只讲 A8W4（本目录的 `*_a8w4.py` 与入口 `aiter/ops/flydsl/moe_a8w4.py`）；同目录的 FP8 / BF16 两阶段底座不在范围内。

## 1. 目标与范围
<!-- ≤8 行：做什么；输入 / 输出、目标硬件与形状；验收（性能对照谁、精度参考谁）；不做什么。 -->
在 MI308X（gfx942）上提供 MXFP4 权重、FP8 按 token 激活的两阶段 FlyDSL MoE，逐位移植自 pyhip `moe-ptpc-a8w4-r2-M17`（811e03a47e）。
- 入口：`prepare_moe_a8w4_ptpc_weight`（加载时把标准 MXFP4 权重转成私有布局）与 `flydsl_moe_a8w4_ptpc`（bf16 进出，SiLU，可选 `swiglu_limit`）。
- 目标形状：Qwen3.8-Flash-Next TP2 / TP4（H2560 E513 topk11 I320 / 160→192）、MiMo-V2.6-Flash TP8 / TP4（H4096 E256 topk8
  I256 / 512）、DeepSeek-V4.1-Flash TP4（H5120 E384 topk6 I576，swiglu_limit=10）。
- 现有两档：M ≤ 32 走不排序的 decode，其余走排序 + 两个 prefill GEMM；去重 decode、流式两档尚未移植（路线见第 6 节）。
- 验收：bench 85 例逐 case 耗时 ≤ M17 × 1.02（同卡分进程，CUDA graph 重放计时，见第 4 节）；同输入时确定性路径的输出与 M17 逐位一致。
- 精度：对独立 fp32 参考 calc_diff ≤ 1e-3、最大误差 ≤ 4.5%·max|ref|；aiter fp8 per-token 只作性能参照（第 4 节）。
- 不做：EP / expert_mask、bias、SiLU 以外的激活、预量化输入、gfx950；接入 `aiter.fused_moe` 分派在路线上。

## 2. 总体设计
<!-- ≤35 行：数据流图（≤12 行）；分档表；每个核心 kernel ≤8 行伪代码（tile 划分与流水线的骨架，不写寄存器与偏移）。 -->
权重在寄存器里按每 32-K 组的 LUT 解成 fp8 走 fp8 MFMA；激活按行量化成 fp8，与参考的量化点逐位一致；按 M 分 decode / prefill 两档。
```text
加载时 prepare_moe_a8w4_ptpc_weight：mxfp4 → 私有布局（按 MFMA K 序排的 fp4、每 32-K 组 delta、每通道因子），I 补零到 64 的倍数
flydsl_moe_a8w4_ptpc（bf16 x[M,H] → bf16 out[M,H]；无 host 同步，可被 CUDA graph 捕获）：
  decode：[行量化(x)] → Gate/Up decode（WG 管一条路由）→ mid f32 → [行量化(mid)] → Down decode（WG 管一个 token）→ out
  prefill：Opus moe_sorting（BM64）→ row_quant_fp8(x，顺带 loc_ids 置 −1) → Gate/Up prefill（gather xq 行）→ mid f32
    → row_quant_fp8(mid) → Down prefill（× 通道因子 × ms × 路由权重，写 loc_ids）→ routes bf16 → sorted_sum（底座）→ out
```
| 输入范围 | 路径 | 为什么 |
|---|---|---|
| M ≤ 32，H ≤ 4096 或 5120，mid 行放得进 LDS | decode：不排序、不规约 | 排序块几乎全是填充；M=1 快 2.7–5.8 倍 |
| （decode）H ≥ 4096 且 I_pad%128=0（MiMo） | 只到 M=20，之后 prefill | 逐路由重读权重，TP4 M24 慢 3% |
| （decode）M·topk·I_pad/16 ≥ 2560 | 先用行量化 kernel 量化 x | 免得每个 WG 各量化一遍整行 |
| （decode）M ≥ 4，w2 < 4 GiB，放得下 | 先量化 mid，Down 用槽对版 | 一条 16 B 加载覆盖两个槽 |
| 其余 M；给了 tile 参数 | prefill：BM64·BN128·TK256 | 多行共用权重；tile 参数只给 prefill |
| （prefill）M > 2048 | Gate/Up 改用 TK128 | LDS 与寄存器减半，大 M 占用更高 |
| （prefill）I_pad ≥ 256 且排序块少 | Down 把 H 切给 2 / 4 个 WG | 末轮 WG 少空闲（MiMo M2048 快 10%） |
| （prefill）I > 512 且估计 WG > 80 | Down 的激活分两段经 LDS | LDS 36 → 20 KiB，每 CU 2 个 WG |
| （prefill）H ≥ 5120 且路由 ≥ 16384 | 两个 GEMM 用按 XCD 分块的 grid | 同块、同 expert 共用 L2，快 1–4% |
核心 kernel 骨架（完整的 Gluon 风格写法、任务划分与逐拍流水线见 [kernels.md](kernels.md)）：
```text
Gate/Up prefill：grid (2I/128, 排序块)，4 wave 管 TILE_M 行 × 64 gate 与同号 64 up；权重进 VGPR 提前 2 tile，x 经 LDS 双缓冲
  每 lane 16 B 读相邻两行 → 每 128-K 步建 LUT → 解码 → MFMA；epilogue 跨 lane 换回 → SiLU(gate)·up → f32 写 mid
Down prefill：grid (切分 1/2/4, 排序块)，bm 行 mq 经 LDS（I>512 可分两段）装入后驻留 VGPR；逐 64 列块解码 → MFMA
  → × 通道因子 × 行 scale → bf16 经 LDS 写 routes；最后写有效路由的 loc_ids
Gate/Up decode：grid (I/16, M·topk)，4 wave = gate / up × K 前后半；序言一次发出全部权重加载，每 lane 16 B 覆盖两个 64-K 块
  x 行（WG 内量化或读预量化行）放 LDS 作广播的 A 操作数；4 个 wave 的部分和经 LDS 相加 → SiLU(gate)·up → f32 写 mid
Down decode：grid (H/16, M)，wave 按槽取 mid 行（WG 内量化或读预量化行，槽对版一条 16 B 覆盖两个槽），经 LDS 换成 A 布局
  → 解码 → MFMA → × 通道因子 × 行 scale × 路由权重；各 wave 的部分和经 LDS 树形相加 → bf16 直接写 out（不清零、不规约）
行量化：每行 L 个 lane，整行进 VGPR；amax → scale = amax/240 → 倒数乘加两次 FMA 修正（正确舍入的商）→ cvt_pk_fp8
  decode 版每行一个 wave、lane 读 16 B 片，DPP + readlane 求 amax，逐元素 IEEE 除法，与上一版逐位相同
```
截断（`swiglu_limit` L>0）：Gate/Up 收尾在乘完通道因子与 xs 后、SiLU 前令 gate ≤ L、|up| ≤ L；L 是编译期常量（kernel 名加 `_swiglu`）。

## 3. 关键决策
<!-- 3–6 条；“为什么”给一个关键数字。 -->
主线是逐位移植 M17、只改 aiter 规则要求的部分：prefill kernel 只差 import 与 FlyDSL 0.5.3 的两处修正，decode kernel 的 ISA 与 M17 逐行相同。
| 决策 | 备选 | 为什么 | 代价 / 限制 |
|---|---|---|---|
| fp4 经 LUT 解成 fp8 走 fp8 MFMA | 解成 bf16（A16W4） | gfx942 无 fp4 MFMA；bf16 的 MFMA 与解码 VALU 都翻倍 | delta > 11 的组按 0 |
| 私有布局按 MFMA K 序预排，加载时转一次 | kernel 内重排标准布局 | 每 lane 每 64-K 读 8 B 即 2 条 MFMA 操作数 | 需 prepare；同 dense GEMM 的 fd2 |
| 行量化的商逐位等于 IEEE 除法 | aiter HIP 量化（乘倒数） | 量化不翻转，与 M17 / 参考逐位一致 | 倒数 + 两次 FMA；scale < 2^-64 逐元素除 |
| M ≤ 32 不排序；decode 每 lane 16 B 读两块 | 全走 BM64 prefill；每 lane 8 B | M=1 快 2.7–5.8 倍；访存指令减半 | 只用半数 MFMA 输出；多 4 个 kernel |
| 保留 M17 的 raw rocdl / buffer op，逐处注明缺的稳定 API | 改写成 typed API | 改写会变 ISA，危及逐位一致与性能 | 依赖 FlyDSL 0.5.3 的 raw 方言接口 |
| 编译句柄缓存按 device 与影响构建的模块常量作键 | 只按形状（M17） | 句柄只能在编译它的 GPU 上发射（AGENTS.md） | 形状不变时无额外编译 |

## 4. 性能与精度
<!-- ≤15 行，写在生成块前面。 -->
decode 档让 M ≤ 32 的 28 例比 prefill 快 1.09–5.8 倍（85 例累计 1.235×）；Qwen 34 例中 32 例快于 aiter fp8 per-token（0.67–0.98 倍耗时）。

|---|---|---|---|---|---|---|
| 1–2 decode | 0.82–0.88 / 0.85–0.86 | 0.77–1.27（≤24%） | 1.22–1.93（≤36%） | 2.8–4.9 | 2.4–4.0 | launch 与固定开销为主 |
| 4–32 decode | 0.68–0.76 / 0.67–0.78 | 1.41–2.15（≤41%） | 2.03–2.75（≤52%） | 5.6–10.6 | 4.3–7.7 | 访存指令条数受限 |

| ≥ 2048 prefill | 0.87–0.94 / 0.80–0.95 | 0.15–1.08 | 0.21–1.71 | 143–265（≤44%） | 135–250（≤41%） | 算力与功耗墙 |
- MiMo / DeepSeek 只测本实现（aiter 无调优表）：decode 0.90–2.27 TB/s（≤43%），M ≥ 2048 时 163–321 TFLOPS（≤53%）；逐 case 见生成块。
- 性能对照：`aiter.fused_moe` per_Token（ab0223ec4e）与本实现同进程、同一 `bench_time_us`；同一 BF16 权重按通道量化成 fp8（TP4 补零）。
- 对照所选：只 Qwen 34 例，断言命中自带的 qwen38 调优表；M ≤ 8、M ≥ 2048 多为 FlyDSL gfx942，M128–1024 为 asm 1 阶段。
- 计时：`run_perftest` 101 次、只计 kernel 时间、权重轮换 32 GiB、预热 ≥18 ms；GPU 须 PTL Enabled（VECTOR,F8），门禁自动检查。
- 表中数字取本实现在 PTL Enabled 下的一次完整 bench；生成块的复核测于整机复位后 PTL 未启用的窗口（prefill 慢 20–30%），只看相对加速。
- 验收对照 pyhip M17（FlyDSL 0.5.0）：同卡分进程 CUDA graph 重放（先连续重放 ≥18 ms 再计时）4 轮 ABBA，各轮中位数之比 ≤ 1.02；A-A 噪声 0.975–1.009。
- 对 M17：同路径 37 例输出逐位相同；逐路由 decode 的 17 例 graph geomean 1.0016、16/17 过（tp2_m32 1.023），eager 1.011、4 例超 1.02。
- 精度：独立 fp32 参考（MXFP4 精确反量化，输入与中间按行 fp8），bench 最大误差 decode 0.95%、prefill 1.83%；真实权重见 [pyhip 文档](https://github.com/luocheng25/pyhip/blob/moe-ptpc-a8w4-r2-M17/src/pyhip/ops/moe/flydsl/moe_gemm_2stage/README.md)第 4 节（模型参考的 0.48–0.98 倍）。

## 6. 风险与待定
<!-- ≤5 条：风险 → 影响 → 打算。 -->
主要差距是去重 decode 与流式两档未移植；路线：M2 去重 decode（含 H5120 只去重 Gate/Up）→ M3 流式与 prep → M4 int9-A2 → M5 接入分派。
- MiMo M2–32、DS M8–32 仍走逐路由 decode 或 prefill（MiMo 形状 decode 只到 M20）→ 比 M17 慢 5–37% → M2 移植去重并删掉 M20 门槛。
- M33–2048 仍是 Opus 排序 + prefill（M17 为流式档与 prep）→ 比 M17 慢、TP4 M48–64 慢于 aiter → M3 移植，85 例对 M17 全量验收。
- 短 decode 例的计时受 GPU 状态影响（PTL、eager 下背靠背降频、graph 噪声 ±2.5%）→ tp2_m32 对 M17 1.023 未过 → 加 PTL 门禁，M3 同协议再测。
- 底座 `sorted_sum` 的编译缓存不按 device → 同进程多卡调用可能在错的 GPU 上发射 → 底座不在本任务范围，报给上游。
- 依赖 FlyDSL 0.5.3 的 raw 接口，门槛只在 MI308X（4 个 XCD）上调过 → 升级或换卡可能变 ISA、不再最优 → 重跑逐位对照与 bench。
