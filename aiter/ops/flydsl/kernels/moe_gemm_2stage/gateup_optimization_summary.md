## 3. 基线 23ca84c6

### 3.1 Kernel 结构（BM256）

- 每个 task 处理 256 行 sorted route，输出 128 列：gate 和 up 各 128 列，计算 SiLU(gate)·up。K tile 为 128。
- 8 个 wave（512 线程），half-M 单 FIFO 流水线，LDS 分两代（t/u）做乒乓：A 的上下半各两个 M slice、B 的 gate/up、scale A，共约 135.6 KB。
- 每个 K tile 有 8 个 phase（TL/TR/BL/BR × slice s0/s1）。每个 phase 依次是：LDS 读 / DMA 发射 / 等待，然后 `lgkmcnt(0)` + barrier，然后 DOT，最后 barrier。
- DOT：每个 (m0, n0) 先用 4 条标量 FP32 FMA 把上一个 phase 的部分和乘以 scale 累加进 C，再发一条 `v_mfma_f32_16x16x128_f8f6f4`，FMA 与 MFMA 交错。launch 带 `-packed-fp32-ops`，防止编译器把 FMA 打包。
- scale B 用 inline asm `s_buffer_load_dword` 读入 SGPR。不用编译器生成的标量 load，是因为 LLVM `lowerSBuffer()` 会丢掉 MachineMemOperand，导致多插 waitcnt。
- wave 4–7 比 wave 0–3 晚一个 barrier（stagger），结束时用 `if wave_id < 4: s_barrier()` 补齐。

BM256 的 phase 表（取自 e2d11fe0 中 `full_tile` 的 docstring，主循环与 23ca84c6 相同）：

| Phase | MFMA | DQ（VALU） | LDS 读（slot） | DMA（slot, tile）/ 等待 |
|---|---|---|---|---|
| TL s0 | A00·B0 | BR s1 (k−1) | A00, SA00 (t) | A1 (u, k+1) |
| TR s0 | A00·B1 | TL s0 | B1 (t) | — |
| BL s0 | A10·B0 | TR s0 | A10, SA10 (t) | B0 (t, k+2) |
| BR s0 | A10·B1 | BL s0 | — | B1 (t, k+2) |
| TL s1 | A01·B0 | BR s0 | A01, SA01 (t) | — |
| TR s1 | A01·B1 | TL s1 | — | A0 (t, k+2) |
| BL s1 | A11·B0 | TR s1 | A11, SA11 (t) | vmcnt(6) |
| BR s1 | A11·B1 | BL s1 | B0 (u, k+1) | SA (t, k+2) |

Ahs = A[半 h, M slice s]，B0/B1 = gate/up，SA = scale A，t = tick，u = 1 − t。TL s0 还会读入两个 scale B SGPR。

### 3.2 23ca84c6 自身的收益（相对 d9608749）

同一套输入下做 A/B：random 路由 46 个 shape，balanced 16 个 shape。

| 比较 | random | balanced |
|---|---|---|
| 纯重写（k_rotate=0），整链 | 1.002× | 0.993× |
| k_rotate 按 tune 结果选择，整链 | 1.005× | 1.015× |
| k_rotate=1，只看 GateUp | 0.980× | 1.050×（最高 1.167×） |

### 3.3 实现整理（refactor，已并入 23ca84c6）

- `compute()` 去掉 inline asm，改成 4 次 `fx.fma` → `sched_barrier` → MFMA intrinsic → `sched_barrier`，不使用 packed FMA。
- 没有改用 `fx.gemm`：FP8 寄存器 fragment 在 `fly-promote-regmem-to-vectorssa` 中无法完成提升（报错 "register operand/result remain after rmem SSA promotion"），因此保留 intrinsic。
- 发现 `-packed-fp32-ops` 会阻止 `__ockl_get_num_groups`（即 `fx.grid_dim.x`）内联。它的返回值落在 VGPR，编译器因此生成 16 个 waterfall 循环。修复方法是显式传入 `num_expert_blocks * n_tiles`；step2 的 worker 数沿用这一做法。
- waitcnt 改为关键字形式（`lgkmcnt=0`、`vmcnt=6` 等），去掉手写的 bitfield。
- 验证：11/11 个 case 逐位一致；主循环关键指令数不变（64 MFMA、256 条标量 FMA、0 条 pk_fma、32 个 barrier、16 个 waitcnt 且操作数相同、4 条 s_buffer_load、48 条 ds_read_b128）；VGPR 从 246/248 降到 240，没有 scratch；性能 A/B 的比值在 0.993–1.001 之间，属于噪声。

## 4. 问题定位：稀疏路由下 BM256 下半块空转

### 4.1 现象

moe_sorting（block = 256）把每个 expert 的 route 依次填进 256 行的块，有效 route 总是块的前缀。如果一个块只有不超过 128 个 route，它的下半 128 行全是 padding，但 BM256 仍然为这一半做 A 的 DMA、MFMA 和 store，大约一半的计算被浪费。

- 典型场景：T=4096、E=256、topk=8，每个 expert 正好 128 个 route，所有块的下半都是空的。
- 在 §7.3 的 280 个模型 case 中，有 80 个 case 的所有块都是这种半块，主要集中在 T=2048/4096。

### 4.2 探索 1：独立的 M128 kernel（dafe8150）

- 从 bm128.py 原型移植的 128 行 persistent GateUp：8 wave、2/3 级 LDS ring、跨 task 预取、XCD swizzle，读 sort128 的元数据。
- 每 expert 80–96 个 route 时，GateUp 比 BM256 快 1.20×（16 个 case 的几何平均，范围 1.011–1.260，用 run_perftest 连续 launch 计时；单次 launch 计时约为 1.07×）。
- route 再多一些就变慢了。阈值扫描按「下半被使用的块比例」（F/B）分组，BM256 耗时 / M128 耗时如下：

| F/B | case 数 | BM256 / M128 几何平均 | 范围 |
|---|---|---|---|
| [0.00, 0.05) | 15 | 1.096 | 0.982–1.219 |
| [0.05, 0.15) | 1 | 1.083 | — |
| [0.15, 0.25) | 8 | 1.034 | 0.970–1.106 |
| [0.35, 0.50) | 6 | 0.909 | 0.826–0.975 |
| [0.50, 0.75) | 7 | 0.828 | 0.738–0.892 |
| [0.75, 1.01) | 11 | 0.759 | 0.651–0.821 |

原因在于 persistent M128 的波次量化：task 数翻了一倍，多出来的一点点半块也会多占一整波。

### 4.3 探索 2：Option A，sort256→sort128 压缩 + M128

在设备端把 sort256 的元数据压缩成 sort128（与 moe_sorting(128) 的结果等价），然后跑 M128。压缩本身耗时 4.4–7.4 us。共 24 个 case：

| T | GateUp | E2E |
|---|---|---|
| 4096 | 1.210×（1.086–1.266） | 1.041×（1.011–1.071） |
| 8192 | 0.705×（0.615–0.784） | 0.843×（0.757–0.936） |
| 16384 | 0.956×（0.855–1.076） | 0.971×（0.914–1.009） |

只有半块占多数时才有收益，因此必须根据路由情况来选择。

### 4.4 探索 3：设备端自动选择（f316a229）

- 压缩 kernel 顺带统计有效的 256 行块数和被使用的 128 行半块数，然后在设备端按波次规则选择：当且仅当 ceil(halves·n/256) ≤ 1.125·ceil(blocks·n/CUs) 时用 M128。如果每个 expert 平均有 128 个以上的 route，host 直接选 BM256。
- 两个 kernel 都会入队，没被选中的那个在 valid-prefix 检查处直接退出。整个过程不需要 host 同步，可以放进 CUDA graph。
- 28 个 shape 的 E2E：auto 相对 BM256 为 1.003×（最高 1.067×）。分情况看：选中 M128 时 +3.0%；设备端选 BM256 时 −1.5%（多付了压缩和一次空 M128 launch 的开销）；host 直接走 BM256 时持平。
- 小结：额外 launch 和压缩的固定开销抵消了大部分收益，而且只能整个 kernel 二选一。

### 4.5 思路转变

BM256 本来就是先算上半 128 行、再算下半 128 行。与其换一个 kernel，不如在 BM256 kernel 内部按块跳过空的下半。这样既不需要压缩，也不需要额外的 launch，选择的粒度也从整个 kernel 细化到了每个块。

## 5. Step 1（3bc0b504）：按块选择 BM256 / 128 行双流水线

### 5.1 设计

- 判定：有效 route 总是每个 256 行块的前缀，所以只需看 sorted 第 128 行：`bottom_id = readfirstlane(sorted_ids[128])`，`bottom_used = token < num_tokens && slot < topk`。每个 WG 只做一次标量判断。
- 下半有 route 的块：走原来的 BM256 流水线，主循环与 23ca84c6 的 opcode 完全一致。
- 下半为空的块：走 128 行流水线（phase 顺序沿用 M128 kernel 的 L0/R0/L1/R1），跳过 A 下半的 DMA、下半的 MFMA 和 store。
- 两条流水线共用 DMA、LDS 读、DOT、store 这几个 helper。store helper 改为显式接收 valid 计数和 C 描述符。
- FlyDSL 的 auto-carry 会跨分支捕获同名变量，因此 128 行分支里的变量统一加了 `half_` 前缀。

### 5.2 128 行流水线（每个 K tile 4 个 phase）

| Phase | MFMA | DQ（VALU） | LDS 读（slot） | DMA（slot, tile）/ 等待 |
|---|---|---|---|---|
| L0 | A00·B0 | R1 (k−1) | A00, SA00 (t) | — |
| R0 | A00·B1 | L0 | B1 (t) | B0, A00 (t, k+2) |
| L1 | A01·B0 | R0 | A01, SA01 (t) | vmcnt(8)；B1 (t, k+2) |
| R1 | A01·B1 | L1 | B0 (u, k+1) | vmcnt(5)；A01, SA (t, k+2) |

- vmcnt 的推导：每个 tile 补充 7 条 VMEM（B0 两条、A00 一条、B1 两条、A01 一条、SA 一条）。L1 的 `vmcnt(8)` 保证 B0(k+1) 在 R1 读它之前到达；R1 的 `vmcnt(5)` 保证 k+1 的所有操作数在下一个 L0 之前到达。
- 为此，prologue 中 tile 1 必须按稳态顺序发射：Bl、At0、Br、At1、SA。
- step2 在这张表的基础上加了两处：L0 在 task 的最后一个 tile 额外发射下一个 task 的 A 下半；两处 vmcnt 也随之变为 `8 + l1`、`5 + r1`（§6.2）。

### 5.3 验证与性能

- 18 个 case 与 23ca84c6 逐位一致，覆盖 k_rotate 开/关、K/128 = 2..56、第 128 行的边界。BM256 主循环的 opcode 一致。
- GateUp 耗时（us，run_perftest）：

| case | 23ca84c6 | step1 | 加速比 |
|---|---|---|---|
| T4096 I256 H7168 E256 top8，balanced（128 route/expert） | 254.3 | 209.0 | 1.217× |
| 同上，H4096 | 156.4 | 125.6 | 1.245× |
| 同上，I512 | 293.4 | 235.8 | 1.244× |
| 256 route/expert | 287.1 | 288.6 | 0.995× |

- 遗留问题：
  - 非 persistent 下，半块与整块混合、block 又多的大 T case 有轻微回退（T=16384、E=512、topk=10 时为 0.980×）。
  - 每个块独立启停，流水线的头尾无法与相邻块重叠。

  这两点由 step2 解决。

## 6. Step 2（e2d11fe0）：persistent 双流水线 + 跨 task 预取

### 6.1 目标

- balanced 128 route/expert 时达到独立 M128 kernel 的水平；256 route/expert 时与 BM256 持平。
- 让 DMA 在 task 之间连续流动，消除每个 block 的 prologue/drain 空泡。

### 6.2 设计

1. **persistent grid**：`workers = min(tasks, CU 数)`，每个 CU 最多一个 WG。worker w 依次处理 task w、w+W、w+2W……，每个 task 是一个 (block, N tile)。`persistent=False` 保留一个 task 一个 WG 的旧行为。worker 数显式传入，不用 `fx.grid_dim`（原因见 §3.3）。
2. 每个 task 仍按 sorted 第 128 行选择 BM256 或 128 行流水线。
3. **跨 task 预取**：每个 task 的最后两个 K tile，在稳态补充用的同一 slot 里预取下一个 task 的前两个 K tile。`tile_refs` 给出 A 下半 (k+1) 和 slot (k+2) 的来源 task 与 tile。
   - BM256 tile 本来就提前一个 tile 发射 A 下半。
   - 128 行 task 的最后一个 tile 额外发射下一个 task 的 A 下半。如果下一个 task 也是半块，这条 load 落在 OOB，不搬数据，但仍计入 vmcnt。
   - 这样，full→full、full→half、half→full、half→half 四种切换下，vmcnt 预算都与稳态相同；128 行流水线用 `vmcnt(8 + l1)`、`vmcnt(5 + r1)` 补偿多出来的那条 load。
   - 每个 task 的前两个和后两个 K tile 被 peel 出来单独处理。K tile 少于 4 个时，tile 0 就开始预取下一个 task。
4. **routing 环**：在 task 开始时预取下一个 task 的 routing（256 个 sorted ID 加 64 份 expert ID，每个 wave 两次 VGPR load），写入一个 3 级 LDS 环（下标为 task 编号 mod 3）。解码和输出 store 用到的 ID 都从这里读。
5. **无条件 store**：无效行写到 OOB 地址，半块 task 再补 4 个占位 store。这样 task 之间的 VMEM 条数是固定的，任何切换下 vmcnt 计数都是确定的。
6. **batch 轮转**：每满 256 个 task 为一批，第 b 批整体偏移 b × (37·group_size_m·n_tiles mod 256)，偏移量是奇数个 block。这避免同一个 worker 总拿到同一类 block，比如 expert 交替出现 full/half 的情况。

### 6.3 验证

- 与 23ca84c6 逐位一致：18 个 case × k_rotate × persistent 开/关；另外 8 个 shape 各重复 40 次（stress）。
- 没有寄存器 spill。BM256 和 128 行的 K 循环与 step1 相同，只去掉了循环里「预取越过末尾」的检查。

## 8. 已知问题与后续方向

1. **Kimi-K3 TP8 T=32768 回退**
   - 现象：GateUp step2 / base 为 0.82–0.87×，E2E 为 0.90–0.92×。该 case 有 2688 个块，其中 1/3 为半块，N 方向 3 个 tile。
   - 原因：`persistent=False` 时 step2 与基线相同（1696–1709 us vs 1710 us），说明问题出在 persistent 的静态轮转。批次轮转之后，每个 worker 分到 4–17 个半块 task，模拟的负载 max/mean 为 1.11。
   - 方向：改为动态任务队列（用 atomic 取 task），或者把 `persistent=False` 加入 tune 空间。
2. **FlyDSL 的覆盖缺口**（都在 Down 侧，与 GateUp 无关）
   - I/TP ≥ 1536：没有可用的 Down 配置。8-wave Down 需要把整个 K 放进 LDS，M128 Down 又断言 K == 256。
   - Down 权重 w2 = E·H·I/TP 字节超过 2 GiB（Qwen3.8 TP2、MiMo TP2、Kimi-K3 TP4）：8-wave Down 结果错误或发生内存访问错误。原因是 `weight_shuffled[..., expert]` 的 expert 偏移按 32 位计算，而 GateUp 和 M128 Down 用的是 64 位。
   - Qwen3.8 T=32768：路由后的 [T, topk, H] BF16 Down buffer 超过 wrapper 的 4 GiB 断言。
3. **小 token 数时整层落后于 aiter**（§7.4）：需要从 Down 和固定开销入手。
4. **已有问题，尚未修复**
   - M128 Down 只支持 K=256，但 `Config.unsupported_reason` 放行了 K=512/768/1024。
   - tuned 表里 token 数不是 2 的幂的行永远不会被命中，因为 `get_padded_M` 会取 nextPow2。
   - 5 个字段的配置走的是 k_rotate 启发式规则。
5. **其他尝试**
   - atomic Down（BF16 packed atomic 归约）：实测更慢，已回退。patch 保存在 session 目录的 `files/e2e/down_atomic.patch`。
   - 去掉 moe_sorting 对累加 buffer 的清零（7fa4ed93，单独分支）：输出逐位一致。moe_sorting 耗时从 11.1 降到 10.6 us（T=512、H=4096），从 25.4 降到 21.9 us（T=4096、H=4096），从 29.2 降到 23.1 us（T=4096、H=8192）。

## 9. 实现经验

- **vmcnt 预算要在所有切换路径上一致**：用 OOB 预取和占位 store 让每一段的 VMEM 条数固定，不要条件发射。注意 OOB 的 load 不搬数据，但仍然计入 vmcnt。
- **OOB 的 buffer load 返回 0**：这个值会被解码成合法的 route（token 0、slot 0），所以必须按 index 显式门控。
- **`-packed-fp32-ops` 与 `fx.grid_dim` 冲突**：ockl 函数无法内联，结果落在 VGPR，会生成 waterfall 循环。grid 大小或 worker 数应显式传参。
- **FlyDSL `range` 的 auto-carry**：循环前已定义、循环内又被赋值的名字都会被当作 loop-carried，跨分支的同名变量可能被误捕获。用不同前缀避开。
- **`fx.gemm` 不支持 FP8 寄存器 fragment**：保留 MFMA intrinsic。
- **scale B 的 SMEM load 用 inline asm 实现**（LLVM `lowerSBuffer` 的问题）：它的等待完全依赖 `begin_compute_phase` 里手写的 `lgkmcnt(0)`，调整 phase 结构时必须保持这一点。
- **计时方式会影响结论**：BM256 的 MFMA 量是 M128 的两倍，在连续 launch（run_perftest）时受功耗限制更明显。M128 相对 BM256 的加速比，连续 launch 计时约 1.20×，单次 launch 计时约 1.07×。本文统一用 run_perftest。
